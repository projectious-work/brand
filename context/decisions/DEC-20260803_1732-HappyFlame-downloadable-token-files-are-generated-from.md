spec:
  title: Downloadable token files are generated from brand.yaml, not hand-maintained
  state: accepted
  decision: '`brand/tokens/variables.css`, `tokens.json` and `tailwind.config.js`
    are generated by `scripts/build-tokens.mjs` from `src/data/brand.yaml`. `scripts/check-tokens.sh`
    runs as the first check in `scripts/verify.sh` and fails on two conditions: the
    committed downloads differing from a fresh generation, or `brand.yaml` disagreeing
    with `src/assets/scss/_scales.scss`.'
  context: |
    The three download files were maintained by hand and had drifted badly. An audit against `_scales.scss` found 71 of 85 scale values missing from at least one file. Concretely: neither `variables.css` nor `tokens.json` carried a single one of the three 12-step scales; `tailwind.config.js` carried the light scales but no dark ones and no terminal palette; none of the three carried the semantic colours in either mode. A consumer downloading `variables.css` got `--color-primary` but no `--midnight-3`, which makes almost every rule in the documentation unusable ("muted text is step 11").

    Two latent bugs were in the same file: `--color-bg`, `--color-surface`, `--color-text-*` and `--color-border` were declared only inside the dark-mode media query, so they were undefined in light mode; and `--color-text-muted` was `#6b7a88`, which is 4.10:1 on the dark surface, below AA.

    `src/data/brand.yaml` was already the machine-readable source the documentation renders from, so a second hand-maintained source was the problem, not a missing one. It lacked semantic colours, surface aliases and breakpoints; those were added from the values already in `_scales.scss`, `_demo.scss` and `foundations/color`.
  rationale: |
    One source of truth is the whole point of a token export. The failure mode here was not that someone was careless — it is that three files in three formats cannot be kept in step by hand across a year of changes, and nothing detected the drift because nothing compared them.

    Generating from `brand.yaml` specifically (rather than from the SCSS) means the file the documentation renders from is the file the downloads come from, so a page and a download cannot state different values. The SCSS is what actually styles the site, so the check verifies `brand.yaml` against it as well — that closes the loop without making the SCSS the export format.

    Wiring the check into `verify.sh` matters more than the generator: the repository has no CI, so `verify.sh` is what "the checks passed" means. A generator without a check would have drifted again the first time someone edited a download by hand.
  alternatives:
  - option: Patch the gaps in the three files by hand
    rejected_because: Restores the state that produced the drift. The files would
      be correct on the day and wrong again within a few releases, with nothing detecting
      it.
  - option: Generate from _scales.scss instead of brand.yaml
    rejected_because: The SCSS defines colour but not the type scale, motion, elevation,
      radius, terminal chrome or breakpoints, so it is not a complete source. It is
      also not what the documentation renders from, so pages and downloads could still
      disagree.
  - option: Drop tailwind.config.js and ship only CSS and JSON
    rejected_because: The Tailwind file is the one a consumer is least able to derive
      themselves, because the mode strategy is a real design question. It is now the
      most complete of the three.
  - option: 'Export dark scales behind Tailwind''s dark: variant'
    rejected_because: Tailwind has no built-in colour-mode concept and projects choose
      between class, media and data strategies. Exposing midnightDark/orangeDark/slateDark
      as their own keys lets a consumer wire them to whatever they already use.
  consequences: |
    `brand/tokens/*` must never be hand-edited; the header of each generated file and the check both say so. The workflow is: edit `src/data/brand.yaml`, run `node scripts/build-tokens.mjs`, commit both.

    The exports grew from 62 custom properties to 241, which is a substantial addition to the public surface — every scale step in both modes is now a supported name that consumers may depend on. Removing or renaming one is a breaking change under the repository's own definition.

    Two limits are documented rather than solved: breakpoints are exported as values, not media queries, because a custom property cannot appear in a `@media` condition; and the Tailwind dark scales need wiring by the consumer.

    `variables.css` now emits the dark values twice — under `prefers-color-scheme` and under `[data-theme="dark"]` — so a consumer's theme toggle works when the OS disagrees.
